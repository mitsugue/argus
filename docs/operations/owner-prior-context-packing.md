# 前回材料の完全保持

現在と前回の材料が約49KBずつある場合、完全に同じ根拠だけの参照化では
65,536バイトの格納上限へ収まらない。現在の材料、訂正・反対材料、出典、
受領時刻、前回の説明は削らず、前回材料だけを既存の同じ文脈内へ可逆圧縮する。
通常の圧縮で収まらなければ、16KBずつの独立した区間へ分け、同じ文脈にある
現在材料の限定した範囲を辞書として共用する。辞書そのものは別に保存しない。
別の保存先・取得経路・生成時計は追加しない。

既存の非圧縮形式と完全一致参照の形式は、そのまま読める。新形式は復元後の
全材料のハッシュ・元のバイト数・JSON構造を検証する。展開は65,537バイトで
打ち切り、分割形式は各区間を16,385バイトで打ち切る。65,536バイトを超える
前回材料、区間の不足・入替・追加、辞書の不一致、末尾の追加データ、途中切れ、
不正な参照・ハッシュを拒否する。最終的な格納文脈の上限も65,536バイトを維持する。
現在の材料だけで上限を超える場合や、圧縮後も収まらない場合は保留する。
非公開原本の受入でも新しい形式の格納上限を照合する。旧形式の原版は変更しない。

AIへ渡す前に前回材料を完全復元する。元から全内容が一致する根拠だけは
従来どおり一度だけ渡し、変更された根拠は全文を保持する。入力の選択、モデル、
出力上限、訂正回数は変えない。格納量の削減をトークンや請求額の削減とは扱わない。

新しい文脈のIDと選択台帳は新内容に結び付ける。過去の原版、ID、受領・完了時刻、
回答は再署名・上書きしない。保存と空の別DBへの復元を元の全内容で照合する。
本番の通常作成・保存・実表示の受入は、手元検査や配信受入と分けて確認する。

## 格納バイト数の照合

文脈の格納上限は、既存SQLite保存器と同じ、キーを整列し区切りの余分な空白を
入れないUTF-8 JSONの65,536バイトで照合する。文字列内の空白・改行・数値・
出典・前回の材料や文章は変更しない。余分な区切り空白を入れた別形式の大きさを
格納サイズとして数えない。JSONの非有限値も保存器と同じく拒否する。
新しい圧縮形式の原本受入も同じ数え方にそろえる。実格納65,537バイト以上の
文脈をそのまま採用せず、既存の可逆格納でも収まらなければ従来どおり保留する。
展開上限・全内容の照合・暗号・原版とIDの不変・過去形式の互換読取は維持する。
形式や保存先を増やさず、保存済みの文脈を書き直さない。

なお収まらない通常更新は、既存の本人診断へ工程、格納・現在材料・前回材料・
前回説明のバイト数と件数だけを残す。最後の失敗観測時刻を付けた履歴であり、
後の更新成功を現在の失敗とは扱わない。例外本文・銘柄・材料・URL・鍵は残さない。
診断GETは再構成・収集・AI・保存を起動せず、既存の自動診断読取で記録する。
