# 立花の価格接続・復帰設計（2026-10-06）

日経平均と登録した日本株の価格を既存画面へ接続する。発注・口座照会・BUY・保有管理は対象外。
暗号資産・投信は従来の価格経路を維持する。実装と検査、実測、本番受入は別の状態。

| 項目 | 方針 |
|---|---|
| 入口 | feature_retired固定停止を設定停止へ戻す。ENABLED=falseを維持 |
| データ | 価格・前日値・価格時刻等の8項目を10秒間隔で一括取得。EVENTや板は起動しない |
| 対象 | 既存の認証済み登録銘柄保存先の日本株。最大50件、未確認の指数を勝手に追加しない |
| 指数 | 公式指数マスタに101=日経平均の記載あり。ただし本人の1回試験が済むまでNIKKEI_CONFIRMEDは設定しない |
| 安全 | 03〜06時はログアウトも送信しない。最初のエラーで当日停止、再試行なし。最大6ログイン/日 |
| 再起動 | 非公開の永続ディスクに日付・回数・停止フラグだけ保存。破損時は送信禁止。仮想URLは保存しない |
| 接続担当 | ローカルの専有ロック＋一台だけを運用担当にする。本番稼働中はMacの試験をしない。別ホストをまたぐロックではない |
| 表示 | 影モードでは通常の価格へ反映しない。表示承認後も15秒超・日付不明・時刻不明は既存価格へ戻す（分単位の価格時刻の扱いは下記2026-10-22） |
| メモリ | 手元の合成負荷、次に2GB本番での影実測。配置は未決定、追加サービスの費用も未承認 |

現行の設定名：ARGUS_TACHIBANA_ENABLED（false維持）、ARGUS_TACHIBANA_RUNTIME_APPROVED
（実測後の配置決定まで未設定）、ARGUS_TACHIBANA_POLICY_PATH（永続・非公開保存先）、
ARGUS_TACHIBANA_NIKKEI_CONFIRMED、ARGUS_TACHIBANA_DISPLAY_APPROVED（表示受入まで未設定）。
ARGUS_TACHIBANA_SYMBOLSは本人の試験・影測定用の明示した対象のみ。通常は既存登録を読む。
銘柄の追加削除を受信中に反映する接続は、単一セッションを保って登録保存先の再読込（現行最大5分）後の一括価格要求に反映する。

受入：指数の実価格／価格時刻と受信時刻／欠測／複数株／静止時間／当日停止／再起動後の上限／
二重起動／本番RSS最大と増加量／API応答時間を確認。合成入力は実価格到着の証明にしない。
表示承認は記録してから設定。今は実測未実施・表示未有効・配置未決定。

公式仕様：https://www.e-shiten.jp/e_api/mfds_json_api_ref_text.html （2026-10-06参照）。
本人の指数試験は本人が1回だけ行う。開発者はログインしない。秘密情報と保護された応答は公開しない。

影の測定道具は scripts/tachibana_price_measure.py。引数なしでは通信0回でNOT_RUNを返す。
本人の指数試験と他端末の停止確認後に、明示した銘柄・永続保存先で1回だけ実行する。
ENABLED環境値を変更せず、単発の影セッションのRSS・コンテナ全体メモリ・要求時間・鮮度件数を測る。
公開Actionsでは実行しない。価格・登録銘柄名・応答本文は出さず、結果は製品外の非公開場所に保存する。
2GB環境で通常負荷と同時に測り、ピーク・増加傾向・既存応答時間への影響から配置を決める。
計測は配置決定の根拠であり、この道具の追加自体を本番計測済みとは数えない。

## 日次記録がない場合（2026-10-07）

記録の欠落をログイン0回と解釈しない。ファイルがない・壊れている・専有できない場合は、
通信前に停止する。初回の使用回数とエラー有無が不明なら、影測定とは別の
`--initialize-blocked-policy --exclusive-owner-session --policy-path <永続の非公開保存先>`
で当日停止の記録を作る。通信は0回、設定は変更せず、既存記録は上書きしない。
count=6は初期使用不明の日の予約枠であり、6回ログインしたという実測ではない。
同日の解除には使わない。翌日以降に、他端末から利用されていないことと一台運用を
確かめてから測定する。03〜06時の禁止、当日停止、6回上限は維持する。

## 分単位の価格時刻の判定（2026-10-22 オーナー判断）

オーナー指示「立花は分単位の時刻の判定の見直し」。PRICEの価格時刻（tDPP:T）は「時:分」で、
秒が無い（精度の印 MINUTE）。従来の「価格時刻から15秒以内ならFRESH」をそのまま当てると、
その分の最初の15秒しかFRESHにならない。10/08の診断では7件中2件、10/22 15:01の本番では
読んだ時点から26秒前の値でも全件DELAYED・状態DEGRADEDとなり、画面は従来の遅延価格に戻っていた。

新しい判定（実装 `argus_providers/tachibana/normalization.py` の `fresh_age_limit_seconds`、
共通の採用判定 `argus_tachibana_live.row_trade_current`、画面 `tachibanaTradeTimeCurrent` /
`nikkeiLiveCurrent`）：

| 価格時刻の精度 | FRESHの条件 |
|---|---|
| 秒まである（SECOND）・精度の記載なし | 受信から15秒以内、かつ価格時刻から15秒以内（従来どおり） |
| 分単位（MINUTE） | 受信から15秒以内、かつ価格の分の始まりから75秒以内（＝その分か直前の分） |

- 根拠：分単位の時刻は「その分のどこか」で約定したことしか示さない。最も新しい可能性の時刻は
  分の終わり（分の始まり＋60秒）であり、そこへ従来の15秒を当てる。FRESHになりうる最大の古さは
  75秒で、2分以上前の値はFRESHにしない。
- 15秒の輸送の新しさ（受信時刻）は維持する。FRESHの期限は「分の始まり＋75秒」と「受信＋15秒」の
  早い方で、次の取得で更新されなければ切れる。
- 受信時刻を約定時刻に置き換えない。表示する時刻は価格の分のまま、「（分精度）」と付ける。
- 秒が0の秒単位の時刻は分単位として扱わない（本当の秒の時刻を最大75秒まで新しいと誤るため）。
  分単位の時刻は分の境目（秒0）でなければ採用しない。
- 日付不明・時刻不明・未来の時刻・市場が閉じている時は従来どおり採用しない。
- 日経平均（101）も同じ判定を使う（`argus_index_live.current_quote_safe`）。101が対象に入るのは
  Renderの環境値 `ARGUS_TACHIBANA_NIKKEI_CONFIRMED=true` の時で、設定はオーナーが行う。
  日経の場中値には `tradedAtPrecision` を付け、画面は分単位なら `delaySeconds` 75秒まで受け付ける。
- 登録株を既存の価格行へ重ねる経路（`overlayTachibanaLive`）は、汎用のLIVE条件（価格時刻60秒以内）も
  通るため、分の始まりから60〜75秒の間は従来の価格行のままになる。緩めていない。
- 商いの薄い銘柄は最後の約定の分が古いままなので、価格が変わっていなくてもDELAYEDのまま。
  これは約定時刻の判定として正しく、受信時刻で補わない。

実装と手元の試験は完了。本番での確認（場中にFRESH件数と状態LIVE/DEGRADEDの内訳を見る）は別に記録する。
