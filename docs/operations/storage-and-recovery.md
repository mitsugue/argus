# 保存の上限と遠隔復旧(2026-10-19 整理)

本番の永続ディスクにある2つの SQLite について、遠隔に何が入っているか、失った時に何を取り直せて
何を取り直せないか、上限に達した時に何が起きるかをコードから整理する。件数と容量の本番値は
`/api/argus/admin/diagnostics/operational` の `archives`(`argus_archive_health`)で測る。
この文書は規則の整理であり、本番の件数や復元の実地確認を意味しない。

## jp_market_source_history.sqlite3(取得元の原本と観測)

| 表 | 中身 | 遠隔(非公開リポジトリ) | 失った時 |
|---|---|---|---|
| raw_sources | 取得元の原本・受領時刻・ハッシュ | 一部のみ(下記) | 対象外の分は公開の原典から取り直せるが、最初に受け取った時刻の証拠は戻らない |
| observations | 原本から作った観測 | 信用残・決算の観測のみ | 原本があれば作り直せる |
| selected_vix_inputs | VIX・日本10年金利の選択行 | なし | 原本から作り直せる(受領時刻は取り直した時刻になる) |
| selected_feature_inputs | TOPIX・米10年・ドル円の初回受領 | なし | 取り直せるが、初回受領の時刻は戻らない |

遠隔に入る原本は `argus_market_input_backup`(`market-analysis/source-inputs/v1`)の許可リストだけ:
信用残の公式原本、決算(財務サマリー)、国債入札の記録、業種ETF(1617〜1633)の日足。

入らないもの: VIXの4本値(Cboe)、日本の金利曲線(財務省)、TOPIX・米10年・ドル円の初回受領。
過去10年分はもともと再取得・再構成で、`historicalVintageVerified=false`(当時の版の確認なし)として
扱っている。失って困るのは、収集を始めてから積み上げた「その日に受け取った」記録だけ。

判断材料(オーナー判断):
1. 許可リストに VIX・金利曲線・初回受領を足す。1回の受領が10年分の CSV 全体なら、日ごとに積むと
   この遠隔保存の上限(全体で128MB、`MAX_ARCHIVE_BYTES`)に早く届く。足す前に本番の `raw_sources` の件数と容量を測る。
2. 足さずに「取り直せる派生データ(初回受領の時刻は失われる)」と明記して運用する。

## market_analysis_history.sqlite3(分析の履歴)

- 表: views(見立ての版)、outcomes、level_map_eps、level_map_mornings、candidate_records。
- 削除の仕組みはない(すべて追記)。
- 遠隔は全件(`argus_analysis_history_compact`、`market-analysis/v2`)。上限は 512組×32件=16,384件、
  元の大きさで1GiB。超えると遠隔保存が「上限超え」で失敗して止まる(黙って欠けることはない)。
- 見立ては13.8.118から平日11回・土日祝2回なので、views は年に約3,000版のペース。ほかの表の分を
  合わせると、数年で上限に届く見込み。正確な時期は本番の件数で測る。

規則(案・オーナー判断):
- 記録は消さない(予測・検証の記録を守る共通要件)。
- 遠隔の件数が上限の8割に達したら、年ごとに分けた次の版の運び方(v3)を作り、v2 は読み取り用に残す。
- 手元のディスクが逼迫した場合も削除はせず、先に容量の内訳を測る。

## 実測(2026-10-19 夜、本番の診断と遠隔の目録)

- 手元: analysis_history 658MB(見立て772版・答え合わせ1,727件)、source_history 68MB。
- 遠隔 v2: 元の大きさ 648.9MB / 上限 1GiB、圧縮後 99.6MB。見立て1版は初めの組で約281KB、最近の組で約950KB。
- このままだと 2026年12月中旬ごろに上限に届き、遠隔保存が止まる見込み(平日11回・土日祝2回のペース)。

最近の1版(約960KB)の内訳と重複:

| 項目 | 1版あたり | 重複 |
|---|---|---|
| 市場の内部(4期間それぞれ) | 83.5KB × 4 | 4つとも同じ(1つの中に全期間の値がある) |
| 市場の特徴(5日の分) | 133KB | 直前の版と同じことが31回中29回 |
| 比較本体(4期間) | 39KB × 4 | 直前の版と同じことが31回中29回 |
| 見立ての文脈の「前回の事実」 | 47KB | 直前の版の事実と31回中31回同じ |
| 財政環境 | 13KB × 2 | 本文と文脈で同じ |

対応:
1. 市場の内部を5日の分に1つだけ保存する(10/19、約250KB=26%減)。読む側は5日の分を見る。古い記録はそのまま読める。
   これで上限に届く時期は約1か月半延びる見込み(年末〜1月上旬)。
2. 残りの重複(前回の事実、版をまたいで変わらない計算)を減らすには、記録の形の変更か、中身ごとに1回だけ
   保存する方式(v3)が要る。上限を上げるかを含めてオーナー判断。

## v3: 部品を1回だけ置く遠隔保存(2026-10-20・オーナー承認)

訂正: v2 の上限は圧縮前1GiBのほかに圧縮後128MBがあり、こちらが先に届く(圧縮後99.6MB、1版約171KB
→11月中旬に止まる見込みだった)。上の「12月中旬」の見込みは圧縮前だけで数えた誤り。

- 実装: `argus_analysis_history_parts.py`。記録の中身・識別・検査は変えず、遠隔に置く形だけを変える。
  1版を骨組みと部品(本文・文脈・各期間の計算のうち2KB以上の項目)に分け、部品は中身のハッシュで1回だけ置く。
  読み取り時刻だけが違う項目(情報の締め時刻など)は骨組みに残す。新しい部品と骨組みだけを圧縮した束
  (1つ512KBまで)にして `market-analysis/v3/` に追記し、前の束は書き換えない。
- 復元は部品から1版ずつ組み立て、組み立てた版のハッシュが元の記録の識別と一致しない時は失敗にする。
- 試算(最新32版): 1版 圧縮前960KB→233KB、圧縮後171KB→48KB。手元の実データ64版の試験では圧縮後
  6.95MB→2.2MB、復元は全版1バイトも違わず、既存ファイルの上書きは0回。
- 上限: 圧縮後512MB、圧縮前4GiB。毎週 `history-capacity` が上限と非公開リポジトリの大きさ(GitHubの推奨
  上限10GB)を測り、どちらかが70%を超えたら失敗して知らせる。数字は非公開側にだけ保存する。

互換の期間と v2 を消す条件:
- 初回の移し替えは1回の同期で最大48版ずつ進み、v3 が手元の全記録を持つまで v2 も書き続ける。
  v3 が失敗した時も v2 を書く。
- v3 がそろった後、v2 は読み取り専用で残す(書き込まない)。
- v2 を消すのは、本番で v3 からの復元の試験(一時ファイルへ全件復元し、全版の識別と件数が一致)が通り、
  その後30日たってから。消すかはその時にオーナー判断。消しても GitHub の履歴には残るので、リポジトリの
  大きさを減らすには履歴の作り直しか新しいリポジトリへの移動が要る。
- 古い版を軽くする決まり(例: 1年より前は計算の一式を外し、文章・予想・答え合わせだけ残す)は、警告が
  出た時にオーナー判断で決める。

## 原本の控えの置き直しを減らし、取り直せない表を足す(2026-10-20・オーナー承認「勧めどおり」)

- 実測: 原本の控え(`market-analysis/source-inputs/v1`)は1回 44.6MB で、目録を作るたびに86個の塊が
  すべて新しくなっていた(原本をハッシュ順に並べ、1本の流れを先頭から切っていたため)。置き場の塊は
  1,421個・740MBで、非公開リポジトリ(2.93GB)が大きくなった最大の原因。
- 変更: 行を入った順に並べ、種類(原本・観測・受け取りの記録・選んだ行)ごとに別の塊にする。新しい行が
  入っても、その種類の末尾の塊だけが変わる。塊をつなげれば今までと同じ形の1本の中身になる。
- 足したもの: `selected_vix_inputs`(VIX・日本10年の日ごとの選択)と `selected_feature_inputs`(TOPIX・
  米10年・ドル円の初回受領)。VIX・金利曲線の原本CSVは毎日全期間が届くため足さない(公開の原典から
  取り直せる)。取り直せないのは「いつ最初に受け取ったか」で、それは選んだ行の表が持っている。
- 置き場に残っている過去の塊と git の履歴は消えない。リポジトリを小さくするには、履歴の作り直しか
  新しいリポジトリへの移動が要る(オーナー判断)。
