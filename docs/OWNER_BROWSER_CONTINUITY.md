# 所有者本人確認と端末の保存結果

この候補は所有者認証、業務readerに依存する。既定OFF。サーバー、画面build、受入readerの三者が同じ状態になるまで本番で有効化しない。

## 挙動と異常系

新しいログイン応答だけでは保存済み本文を開かない。仮sessionを画面へ公開する前に、サーバーのsession確認へ一回nonceを送り、HTTP成功・認証済み・同じnonceを全て確認する。古いSWの200、通信切断、別nonce、確認中のoffline/pagehide/logout、後着応答は本文を開けない。パスキーにも同じ確認を使う。

オフラインへ移った時点で短期memory sessionを破棄し、保存結果を消さず本人確認画面へ戻る。offline中は認証操作を無効化する。onlineに戻っても自動解除せず、通常の本人確認を要求する。保存形式、履歴、描画、設定の移行や削除は行わない。サーバーへ届かなかった失効は既存30分の期限が上限であり、即時失効を保証したとは扱わない。

## 自動受入

既存 `ARGUS_ACCEPTANCE_OWNER_AUTH` を1にした場合だけ、owner origin/passwordの明示設定を使う。各contextとreloadは通常画面の復旧用passwordを入力する。admin/sessionのブラウザ注入や永続化はしない。終了とonline reload前には通常logoutのnonce応答を確認する。既存10回/分の制限を変えず、同じ実行内のUI認証を7秒以上空ける。429は失敗であり自動再認証しない。

M01–M15、12組合せ、候補版、既存時間制限、225msの表示条件は維持する。M13の認証ONはofflineで本人確認画面と保存領域の完全一致を確認し、online本人再認証後の同じsnapshot IDを要求する。認証OFFは従来のoffline本文表示を検査する。制御されたAPI応答も、その要求のnonceを返す。他のAI/注文等POSTを認証例外に含めない。

認証情報をconsole/network本文へ出さず、password入力はスクリーンショットでmaskする。検査プロセスはsecret/tokenをmemoryだけで保持し、閉じたprofileと証跡をUTF8/UTF16/URL/JSON表現でも検査する。秘密やsymlink等の不正を検出した場合は合格markerを作らず、認証ONの証跡公開を停止する。既存profile sanitizationは合成の検査profileだけを対象とし、本人の実ブラウザ保存内容は削除しない。この検出は端末の暗号化保管全般を証明するものではない。

## 有効化・旧PWA・切戻しの受入条件

1. 親候補・全readerを正規審査/検査して統合し、版識別を一致させる。まだ公開提出の承認待ちであり、この文書やローカル検査は承認の代わりにならない。
2. 新password/RP/origin・既存admin・復旧手順・受入用secretの配置を本人と確認する。公開GitHubへ所有者データを含むprofile/証跡を送る許可はコード提出の許可と別である。保存先・内容・保持期間の具体的承認なしで認証ONの本番受入を実行しない。
3. 旧端末の履歴/設定/描画を保全し、online更新を確認する。新JSから、既にofflineで動いている旧JSを遡及的にロックできない。キャッシュを消して解決済みとしない。
4. iPhoneホーム画面版で登録、offline/reload、online再認証、元snapshot/履歴/設定、紛失失効とpassword復旧を受入する。共有リンクの未認証本文拒否も確認する。
5. M13含む新しい両modeを本来のブラウザ受入で完走する。今回の合成React/SW/IndexedDB検査を全Today15ゲートや実iPhone受入へ読み替えない。
6. 認証有効化後の問題で匿名公開へ自動切戻ししない。保全した前版の認証対応build/サーバーへ戻すか、本人確認画面を維持して修復する。保存データを消さない。
