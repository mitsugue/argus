# ARGUS v13.4.2 Remote Journal durability closure

## Release truth

This change closes the response-path defect in the Remote Journal receipt
protocol. It does not promote Checkpoint V2, arm Formal Soak, start a Soak,
restart EC2, or mutate production during review.

The v13.4.1 production evidence is internally consistent:

- backend b896cc45a4c2c2382b27d715b5634d2f8f2d6a2f, restart count 0;
- legacy checkpoint authority and Checkpoint V2 validation mode;
- Remote Journal local 400, remote 377, pending 23, failed/poison 0;
- latest completed receipt and WAL read-back are verified;
- applied WAL 3296, remotely verified WAL 3270, leaving 26 unverified.

The degraded signal is real. Recent natural caos-scan runs fail only in
durability-flush: the client gives up at 60 seconds while Render finishes the
same receipt request in approximately 116–117 seconds. The observed server
duration is therefore approximately 116.5 seconds on average and approximately
117 seconds at p95 for the available incident samples. GitHub run 30964948050
corroborates the timeout: the receipt step ran 1m03s and reported
http=None reason=timeout.

One receipt currently serializes one approximately 127 MiB legacy checkpoint
before responding. At 116.5 seconds, theoretical synchronous capacity is about
30.9 receipts/hour, above the configured two receipts/hour arrival rate. The
red runs are consequently a response-latency and contract defect, not proof
that receipt arrival alone exceeds service capacity. Pending journal events
remain cumulative state and still require the SLO gates below.

## Asynchronous receipt contract

POST /api/argus/admin/remote-journal/commit-receipt now:

1. authenticates and validates the exact backend SHA, immutable remote commit,
   compact-state hash, target WAL sequence, and Idempotency-Key;
2. atomically fsyncs a small integrity-hashed intent sidecar;
3. returns 202 Accepted for a new intent or 200 for an exact replay;
4. never serializes the full legacy checkpoint in the HTTP response path.

GET /api/argus/admin/remote-journal/receipts/<operationId> returns public-safe
status only. The receipt's requested commit is kept separate from the newer
cumulative commit that may verify it during coalescing.

Natural mission-tick persistence owns the drain. At most one writer selects up
to 33 eligible intents, verifies the highest cumulative WAL target, performs
the one checkpoint already required by that natural lifecycle, and only then
marks every covered intent verified. A checkpoint failure leaves the intents
pending. Transient failures use bounded exponential retry; permanent failures
or eight exhausted attempts isolate a poison receipt without blocking a newer
valid target. There is no manual tick, manual flush, background busy-loop, or
per-receipt checkpoint storm.

The workflow posts with a 15-second acceptance timeout and bounded status polls
at 5, 10, 20, 40, 80, and 120 seconds. Exact verification is green. A pending
receipt younger than 1,800 seconds is reported explicitly as
pending_within_slo; it is not mislabeled durable. Pending beyond the SLO,
failed/poison status, malformed proof, auth failure, target mismatch, or
read-back failure is red.

## Restart and v13.4.1 migration

The queue is persisted at /var/data/argus_remote_receipt_queue.json by default.
Boot refuses an invalid queue instead of resetting it. A v13.4.1 receipt
sidecar is migrated once: only its persisted remote/verified WAL cursor is used
as a lower bound because the old schema did not preserve the intended target
independently. No higher sequence is guessed. Immutable read-back may verify a
newer cumulative state.

Crash tests cover acceptance fsync, remote verification before local
acknowledgement, restart restoration, duplicate idempotency keys, same-target
distinct receipts, a newer receipt arriving during a drain, writer contention,
and checkpoint failure. Every accepted receipt retains a stable audit ID.

## Owner-approved rollout

1. Merge the reviewed Draft PR only after all required checks pass.
2. Allow one normal Render auto-deploy of the exact merge SHA. Do not restart
   EC2 and do not manually run caos-scan, a mission tick, heartbeat, or
   Remote Journal flush.
3. Verify health, ready, and the release manifest all report the exact merge
   SHA; boot/restart/OOM and persistent-storage integrity must be healthy.
4. Verify the v13.4.1 sidecar is preserved or migrated and the new queue
   integrity is valid.
5. Observe natural drains only. Require failed=0, poison=0, pending bounded,
   oldest pending age <1,800 seconds, exact receipt read-back true, and remote
   WAL catching up monotonically to applied WAL.
6. After durability closure, observe three new and distinct natural Checkpoint
   V2 validation windows.
7. Perform the separately approved isolated V2 restore proof.
8. Stop before Checkpoint V2 promotion and before Formal Soak. Both require a
   separate owner approval.

## Rollback

Rollback is owner-approved and finite. Trigger it for identity mismatch,
restore/integrity failure, cursor regression, stale/tampered receipt
acceptance, unbounded or over-SLO pending work, poison growth, checkpoint
storms, restart/OOM, or memory regression.

Redeploy the last verified v13.4.1 SHA and restore the matching workflow
contract as one controlled rollback. Preserve the new queue sidecar, legacy
receipt, WAL, checkpoint, cursor, and Soak history in place; v13.4.1 ignores
the new queue, and a later corrected v13.4.2 deployment can resume it. Never
delete, rewrite, or manually acknowledge queued receipts as part of rollback.
