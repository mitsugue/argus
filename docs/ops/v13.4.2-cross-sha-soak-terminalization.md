# ARGUS v13.4.2 cross-SHA Soak terminalization

## Scope

This hotfix changes only restore-time projection of a persisted running Soak.
When durable evidence proves that the successor backend build or boot differs,
the old Soak is terminalized as `interrupted`. Its identity, `startedAt`,
heartbeats, interruption history, and `completed72h=false` are preserved.

The hotfix does not start a replacement Soak, arm Formal Soak, promote
Checkpoint V2, flush Remote Journal, run a mission tick, or modify production
state. `planned_owner_restart` remains available only when the existing durable
owner marker is verified.

The release-acceptance durability design and controlled rollout are documented
separately in [v13.4.2-durability-closure.md](v13.4.2-durability-closure.md).

## Deterministic classification

| Persisted state | Build evidence | Boot evidence | Result |
|---|---|---|---|
| running | different SHA | any | `interrupted / backend_build_changed` |
| running | same or missing SHA | different boot | `interrupted / boot_discontinuity` |
| running | missing or ambiguous | missing or unchanged | `historical_evidence_incomplete` |
| already terminal | any | any | preserve persisted terminal truth |

Derived records include
`terminalizationProvenance=derived_from_persisted_build_and_boot_evidence`,
`previousBackendBuildSha`, `supersededByBuildSha`, `previousBoot`, and
`successorBoot`. No evidence path manufactures `completed` or
`planned_owner_restart`.

## Pre-deploy read-only gate

Before owner-approved deployment, record:

1. exact release manifest SHA and successful publication run;
2. current `/healthz` and `/readyz` SHA, version, boot time, restart count;
3. first natural EC2 mission slot and `ec2_systemd` identity evidence;
4. Remote Journal local/remote/pending counts, oldest pending age, receipt SHA,
   WAL read-back result, and auth/rate/poison errors;
5. Checkpoint V2 mode and `formalSoakArmed=false`.

Deployment remains blocked while current Remote Journal durability is not
verified for the current queue. No manual flush or manual tick is permitted by
this runbook.

## Owner-approved rollout sequence

1. Merge the reviewed v13.4.2 hotfix only after every required check succeeds.
2. Deploy the exact merge SHA once through the normal Render release path.
3. Do not restart EC2 and do not trigger a manual mission tick.
4. Verify the previous Soak is `interrupted`, its identity and evidence counts
   are unchanged, and no replacement/Formal Soak started during boot.
5. Observe the next natural EC2 slot and re-check Remote Journal durability.
6. Start Formal Soak only under a separate owner approval after all durability
   and Checkpoint V2 Stage 1 gates pass.

## Rollback thresholds

Rollback to the previously verified production SHA if any of these occur after
an owner-approved deployment:

- health/ready identity mismatch or restore/integrity failure;
- old Soak identity, `startedAt`, heartbeats, or interruptions are lost;
- old Soak is shown as `completed`, a replacement Soak starts during boot, or
  Formal Soak becomes armed;
- Checkpoint V2 mode/authority changes;
- WAL cursor regression, receipt read-back failure, tampered/stale receipt
  acceptance, Remote Journal auth/rate/poison errors, or growing loss window;
- restart/OOM recurrence or sustained memory above the production threshold.

Rollback itself requires explicit owner approval and must not rewrite Soak,
WAL, checkpoint, receipt, or immutable history records.
