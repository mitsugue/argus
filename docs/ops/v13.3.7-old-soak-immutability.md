# v13.3.7 Old Soak immutability hotfix

This patch keeps an archived Soak's terminal result separate from its
relationship to a later backend deployment.

## Contract

- `state`, `status`, and `terminalState` describe the immutable historical
  result. A later deployment cannot replace them with `superseded`.
- `lifecycleRelation`, `supersededByBuildSha`, and (when durably known)
  `supersededAt` describe the later-build relationship.
- `failureClass` is copied from the archived record or derived only from its
  persisted heartbeat evidence. If neither is possible it remains `null` and
  `historicalEvidenceState=historical_evidence_incomplete` fails closed.
- Maximum evidence-gap, interruption, restart, scheduler, completion, and
  formal-result fields are projected from an immutable value copy.
- A deployment alone leaves the active Soak `not_started` with no `soakId`.
  Only the first qualified ordinary `ec2_systemd` mission window may create a
  successor Soak.

## Production recovery behavior

On restore, a legacy compact `previousSoak` summary is joined to the matching
bounded `soakHistory` row by `soakId` and `startedAt`. The history row is the
authority; normalization does not edit it, append duplicates, or invent
missing evidence. Repeating restore/normalization is idempotent.

The legacy `supersededBy` alias remains for compatibility, but is relationship
metadata only. New transitions store the exact 40-character Render SHA when it
is available. A pre-existing short relationship SHA remains explicitly marked
with `supersedingBuildShaExact=false` instead of being expanded by guesswork.
