# Owner authentication activation and recovery

This candidate adds a disabled-by-default owner boundary. It is not evidence
that production is protected. The existing admin and encrypted owner-vault
credentials remain independent. A browser login does not authorize admin
mutations, execution, orders, or overriding existing vault proofs.

## Configuration and browser flow

- Server: `ARGUS_OWNER_AUTH_REQUIRED=1`, `ARGUS_OWNER_AUTH_ORIGIN` equal to the
  exact HTTPS Pages origin (no path), `ARGUS_OWNER_PASSWORD_HASH` generated by
  Werkzeug using scrypt or PBKDF2-SHA256, and `ARGUS_OWNER_AUTH_DB` pointing to
  a new private database on the existing persistent volume. Password entry and
  secret configuration belong to the owner. Do not put a password in source,
  shell history, build variables, artifacts, or a URL.
- Frontend: `VITE_ARGUS_OWNER_AUTH_REQUIRED=1` and the existing exact HTTPS
  `VITE_ARGUS_BACKEND_URL`. Existing CORS must admit the selected origin.
- Cookies are not used. The server verifies a one-use WebAuthn challenge,
  origin, exact RP host, user verification, credential public key, and counter.
  A successful login issues a random 30-minute token held only in JS memory.
  Only its digest is stored by the server. Registration requires an owner
  session; the password remains available for recovery.
- The browser mounts providers/data views only after login and sends the token
  solely to the exact configured backend API origin. Redirects are rejected.
  Authenticated Service Worker requests use NetworkOnly. Each authenticated
  response must echo its fresh random request nonce, so an old worker cannot
  substitute an earlier cached success for the current server session check. Expiry, logout and
  pagehide close the view; late responses from a prior login are rejected.
  A visible page checks revocation every 30 seconds and upon becoming visible;
  a failed revocation check closes the view.
- Password attempts and WebAuthn actions each have a persistent, owner-wide
  10/minute limit. Forwarded IP headers cannot reset it. Remote abuse may
  temporarily delay login; it cannot lock out an existing valid session or
  change operational authentication. Challenges expire at five minutes;
  credentials are limited to 16, sessions to 32, and auth bodies to 32 KiB.

## Recovery and rollback

Password login works with no passkey. The authenticated recovery form requires
that password again and explicitly revokes all passkeys, sessions and pending
challenges. It does not erase market data, owner vault, research, or history.
If a device is lost, use that flow from a trusted device, then enroll new keys.
If the password is lost, the operator sets a new password hash via the existing
private hosting settings. The changed hash invalidates old sessions and
challenges; it does not alter unrelated secrets or stored analysis.

`python scripts/owner_auth_backup.py backup --source <auth-db> --destination
<new-private-backup>` uses SQLite backup, integrity checks, fsync and atomic
no-overwrite installation. The source and existing destinations are retained.
Keep it in existing owner-controlled protected storage, not a public repo or
Actions artifact. This candidate does not upload registry files anywhere.

While the service is stopped, `prepare-restore` with the same arguments creates
a NEW registry file with every old session/challenge/passkey removed. The
source backup retains the original keys for audit; historical keys must not
revive a device revoked after that backup. Use the recovery password and
explicitly enroll the devices again. Retain the current DB, inspect the prepared file, then switch the DB
path and restart with authentication still enabled. Test password login and new passkey enrollment/authentication. Do not restore old live sessions or automatically disable authentication
when a database is unavailable. A database error fails closed. Keep the previous
protected deployment available; rollback must not reopen public data routes.

Authentication storage and backup are small but not yet capacity/billing
measured. This candidate is not 4GB/2GB acceptance or formal 72-hour evidence.
