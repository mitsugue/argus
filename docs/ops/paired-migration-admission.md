# APIと保存形式を連動して移行するための配信検証

日本株分析エンジンの名称移行は、フロントエンド・API・保存形式を同じ候補で
検証する必要がある。既存のProduct証明だけではRecoveryの変更を証明できず、
Recovery証明だけでは画面・配布物を証明できない。

## 許可する範囲

通常の `PRODUCT` と `RECOVERY_ONLY` の検証は維持する。未指定の `MIXED` は拒否する。
`PRODUCT_AND_RECOVERY` は、Recovery実装差分とProduct実装差分のSHA-256がともに
固定値に一致し、製品バージョンが変わらない候補だけに適用する。
Product側の固定値は初期状態では未設定であり、この経路は無効である。
名称移行の最終差分を検証する変更で両方の固定値を設定する。

任意のパスを広く許可する設定や、片方の検査失敗を無視する設定は設けない。
固定範囲外の修正・未知のファイル追加・バージョン変更は従来どおり拒否する。
名称移行後の通常の開発は、通常の分類と証明に戻す。

## 必須となる証明

同一の候補コミット・ツリーに対して、既存のProductシミュレーション2回、
Product証明の発行と取得元確認、Recoveryの対象テストと独立した証明を両方実行する。
Recoveryの証明にはProduct証明も必要であることを明記する。
一方をもう一方の代用にしない。売買権限、校正済み確率、復元権限の昇格は行わない。

マージ前の検証では両方の証明を検査する。Pages配信前にもマージ元の候補と
親コミットから分類を再計算し、GitHub上の正しい実行・試行・成果物に結び付いた
両方の証明を再取得して検査する。古い候補・別のツリー・片方の証明欠落は拒否する。
既存のブランチ保護、必須チェック、配信前のリハーサル、本番の受入確認は維持する。

## 実装・検証・本番の区別

この文書を追加した段階では経路を実装してローカル検証したのみである。
実際の名称移行、端末データの保全、サーバー保存データの変換、配信後確認の完了を
意味しない。これらの証跡は移行台帳で個別に記録する。
