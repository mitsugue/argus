# ARGUS v13.3.6 formal Soak closure

This change is a release candidate. Creating this document, running tests, and
opening its Draft PR do not authorize a merge, deploy, restart, EC2 change,
manual workflow, manual tick, or backend POST.

## Permanent contracts

### Soak start authority

- Only `triggerSource=ec2_systemd` may create a Soak.
- `startedAt` is exactly the natural mission window `scheduledFor`.
- `startedBy` is `ec2_systemd`.
- `firstMissionWindowId` identifies that natural window.
- A GitHub schedule may contribute later continuity evidence but cannot create
  a Soak.
- Manual/diagnostic runs cannot create a Soak.
- A mission window earlier than process boot or restore completion is rejected.

For a same-SHA restart, an authenticated owner may arm one rollover through
`POST /api/argus/admin/soak/arm`. The request must carry `confirm=true` and the
exact 40-character current build SHA. Arming does not start a Soak and does not
alter its clock. The arm is consumed once by the next natural EC2 mission
window. The prior Soak is copied into bounded immutable history before the new
active object is created. A consumed arm cannot create another Soak.

### Formal closure is four separate proofs

`formalSoakClosure` reports these gates independently:

1. 72-hour duration
2. scheduler continuity
3. mission execution success
4. Remote Journal durability

`completed72h=true` is emitted only when all four are true. A healthy mission
cannot hide a missing receipt; a verified receipt cannot hide a scheduler gap.

### Remote Journal receipt

The commit receipt's exact immutable SHA is the read-back authority. The
backend fetches:

`https://raw.githubusercontent.com/mitsugue/argus/<40-char-commit>/ledger/osint/readback.json`

It never verifies a receipt against the moving `ledger` branch. Read-back is
bounded to two attempts. Public-safe telemetry is persisted in the receipt:

- `remoteDurabilityState`
- `receiptCommitSha`
- `receiptCreatedAt`
- `receiptVerifiedAt`
- `receiptAgeSeconds`
- `receiptAttempts`
- `receiptErrorClass`

Transient HTTP/network failures remain distinct from integrity failures.
Examples include `http_502`, `timeout`, `network_error`,
`exact_commit_not_available`, `receipt_hash_mismatch`, and
`remote_wal_sequence_regression`. WAL compaction remains fail closed and only
uses a matching, fsynced, exact-commit receipt.

## Exact rollout order (owner approval required)

1. Confirm PR A and PR B are still Draft and all required checks are green.
2. Rebase each candidate on the latest `main` and rerun full pytest and release
   gates. Do not reuse an earlier green result after the rebase.
3. Merge PR A only after owner approval. It must not deploy the backend.
4. On EC2, run the PR A installer in dry-run mode. Review its allowlisted file
   diff, owner/mode evidence, and checksums.
5. With separate owner approval, apply the installer. Follow the runbook's
   service reload procedure; do not run a mission tick.
6. Merge PR B only after separate owner approval. Permit exactly the intended
   backend v13.3.6 deployment; do not restart the bridge.
7. Verify `/healthz` and `/readyz` report the exact deployed 40-character SHA
   and backend version 13.3.6.
8. Publish the external production release manifest only after both GET
   verifications match. Confirm EC2 resolves that manifest without a static pin.
9. If the restored active Soak is the interrupted same-SHA Soak, send one
   owner-confirmed arm request with the exact deployed SHA. Do not call the
   mission tick.
10. Wait for the next natural EC2 systemd execution. Verify the new Soak has
    `startedAt == missionWindow.scheduledFor`, `startedBy=ec2_systemd`, the
    matching `firstMissionWindowId`, and the old Soak in immutable history.
11. Observe for at least 72 hours. Close only when all four
    `formalSoakClosure` gates pass and restart/OOM/integrity alarms remain clear.

Any identity mismatch, restore failure, receipt integrity failure, WAL cursor
regression, restart, or unverified continuity gap stops formal closure. It does
not authorize a manual tick or clock rewrite.

## Rollback

Rollback requires a separately approved backend deployment and a release
manifest whose `deployedAt` is newer than the manifest it replaces. Never edit
checkpoint, Soak, cursor, WAL, or receipt files directly. The interrupted and
archived Soak records remain evidence and are not rewritten as successful.
