# ARGUS v13.3.6 formal Soak closure

This change is a release candidate. Creating this document, running tests, and
opening its Draft PR do not authorize a merge, deploy, restart, EC2 change,
manual workflow, manual tick, or backend POST.

## Permanent contracts

### Soak start authority

- Only `triggerSource=ec2_systemd` may create a Soak.
- `startedAt` is exactly the natural mission window `scheduledFor`.
- `startedBy` is `ec2_systemd`.
- `firstMissionWindowId` identifies that natural window.
- A GitHub schedule may contribute later continuity evidence but cannot create
  a Soak.
- Manual/diagnostic runs cannot create a Soak.
- A mission window earlier than process boot or restore completion is rejected.

For a same-SHA restart, an authenticated owner may arm one rollover through
`POST /api/argus/admin/soak/arm`. The request must carry `confirm=true` and the
exact 40-character current build SHA. Arming does not start a Soak and does not
alter its clock. The arm is consumed once by the next natural EC2 mission
window. The prior Soak is copied into bounded immutable history before the new
active object is created. A consumed arm cannot create another Soak.

### Formal closure is four separate proofs

`formalSoakClosure` reports these gates independently:

1. 72-hour duration
2. scheduler continuity
3. mission execution success
4. Remote Journal durability

`completed72h=true` is emitted only when all four are true. A healthy mission
cannot hide a missing receipt; a verified receipt cannot hide a scheduler gap.

### Transient-event policy

The following cases do not weaken the gates above:

- A single HTTP 502 is a failed transport attempt. It may recover at the next
  natural slot without a manual retry. It is not a mission-processing success
  for the failed slot. Formal closure remains possible only if the resulting
  evidence gap stays within the configured maximum heartbeat gap and all other
  continuity evidence is valid.
- `verification_pending` is allowed as an intermediate Remote Journal state.
  The Soak cannot formally complete while it is pending. A later bounded,
  exact-commit read-back may turn it into `verified`; integrity failures never
  receive this grace.
- `commit_receipt_stale` without mission-processing failure means local
  mission work and local disk/WAL durability may have succeeded, but remote
  disaster-recovery durability is not verified. It blocks formal completion
  until an exact immutable receipt is verified.
- `partial` followed by `caught_up` within one natural systemd invocation is
  one bounded invocation outcome. Scheduler continuity is unchanged and
  mission processing passes only when the final result is `caught_up` with
  zero permanent skips/poison retries.
- A failed natural invocation is recorded as a mission failure even when it
  does not exceed the maximum heartbeat gap. The bounded gap can preserve
  scheduler/heartbeat continuity, but it cannot relabel that invocation as a
  successful mission. A later natural success may establish the current
  mission gate; the failure remains immutable evidence.

Accordingly, scheduler continuity, heartbeat continuity, mission-processing
success, local disk/WAL durability, remote disaster-recovery durability, and
the formal 72-hour result are six distinct statements. Every slot need not be
immediately remote-verified, but every receipt required for final closure must
resolve to exact-commit verification before `completed72h=true`.

### Remote Journal receipt

The commit receipt's exact immutable SHA is the read-back authority. The
backend fetches:

`https://raw.githubusercontent.com/mitsugue/argus/<40-char-commit>/ledger/osint/readback.json`

It never verifies a receipt against the moving `ledger` branch. Read-back is
bounded to two attempts. Public-safe telemetry is persisted in the receipt:

- `remoteDurabilityState`
- `receiptCommitSha`
- `receiptCreatedAt`
- `receiptVerifiedAt`
- `receiptAgeSeconds`
- `receiptAttempts`
- `receiptErrorClass`

Transient HTTP/network failures remain distinct from integrity failures.
Examples include `http_502`, `timeout`, `network_error`,
`exact_commit_not_available`, `receipt_hash_mismatch`, and
`remote_wal_sequence_regression`. WAL compaction remains fail closed and only
uses a matching, fsynced, exact-commit receipt.

## Exact rollout order (owner approval required)

1. Confirm PR A is merged without a backend deploy and PR B remains Draft with
   all required checks green.
2. Confirm PR B is based on the PR A merge commit and rerun full pytest and
   release gates. Do not reuse an earlier green result after the rebase.
3. Obtain separate owner approval before merging PR B.
4. Merge PR B only after that approval. Permit exactly the intended
   backend v13.3.6 deployment; do not restart the bridge.
5. Verify `/healthz` and `/readyz` report the exact deployed 40-character SHA
   and backend version 13.3.6.
6. Publish the external production release manifest only after both GET
   verifications match and verify its exact published bytes. Keep the static
   pin in place.
7. From the merged PR B checkout, run the integrated EC2 installer in dry-run
   mode. Review its allowlisted file diff, owner/mode evidence, and checksums.
   The new backend fails closed until an eligible natural payload arrives; do
   not compensate with a manual tick.
8. With separate owner approval, apply the installer. It performs no
   daemon-reload, service start/restart, POST, tick, or heartbeat. Keep the
   fixed-SHA pin while the read-only resolver proves manifest/backend equality.
9. Run the installed resolver in read-only preflight and require
   manifest/backend equality. Remove the temporary pin only under the
   runbook's separate approval gate. Do not restart or tick in the same
   operation.
10. If the restored active Soak is an interrupted Soak for the same deployed
   SHA, send one
   owner-confirmed arm request with the exact deployed SHA. Do not call the
   mission tick. A genuinely new build SHA does not require this same-SHA arm.
11. Wait for the next natural EC2 systemd execution. Verify the new Soak has
    `startedAt == missionWindow.scheduledFor`, `startedBy=ec2_systemd`, the
    matching `firstMissionWindowId`, and the old Soak in immutable history.
12. Observe for at least 72 hours. Close only when all four
    `formalSoakClosure` gates pass and restart/OOM/integrity alarms remain clear.

Any identity mismatch, restore failure, receipt integrity failure, WAL cursor
regression, restart, or unverified continuity gap stops formal closure. It does
not authorize a manual tick or clock rewrite.

## Rollback

Rollback requires a separately approved backend deployment and a release
manifest whose `deployedAt` is newer than the manifest it replaces. Never edit
checkpoint, Soak, cursor, WAL, or receipt files directly. The interrupted and
archived Soak records remain evidence and are not rewritten as successful.
