# ARGUS v13.3.8 OOM incident forensics

## Release boundary

This document describes a proposed recovery hotfix only. It does not authorize
a production merge, deploy, Render restart, manual mission tick, manual
heartbeat, or a new Soak. The v13.3.7 formal Soak is interrupted and remains
historical evidence.

## Observed production evidence

- Deployed backend: v13.3.7 at exact SHA
  `9c743f93b9e5bbadc79c8ba891959db3a4e6287c`.
- Formal Soak: `soak-9c743f9-13fa1e4b`, started
  `2026-08-02T08:37:00Z`.
- Render reported that `argus-backend` exceeded its memory limit and performed
  an automatic restart at `2026-08-03T21:07:46+09:00`.
- The recovered process boot is `2026-08-03T21:07:46.615507+09:00`; restart
  count is 1. This interrupts the formal Soak even though the API's operational
  continuity projection reports a verified recovery.
- The durable final checkpoint was 123,973,516 bytes. Runtime storage
  diagnostics reported 1,099,859,035 bytes of checkpoint temporary files,
  WAL 631,910 bytes, and 3,953,586,176 bytes free.
- Natural EC2 systemd slots after recovery completed successfully with exact
  build identity and HTTP 200. Examples:
  `tick-bd02329001574ff6a58150ba30692c24` (processed 10, remaining 0) and
  `tick-daea624f01fc4dcabd068968cb2da826` (processed 0, remaining 0). Both
  reported checkpoint creation and Remote Journal read-back verification.
- The current durable checkpoint remains integrity-valid. WAL read-back
  sequences agreed at 2639 in the captured post-recovery snapshot.

The exact abandoned temporary filename, device/inode and timestamps are not
available from the public API. Render's authenticated shell/log/metrics view
was not available in the evidence session. This is an explicit evidence gap;
the hotfix must not invent those values or load the 1.10 GB file to obtain
them.

## Root-cause classification

### Proven by code and runtime evidence

1. The production checkpoint path built a complete canonical JSON byte string
   before writing.
2. It then read the complete temporary file into another byte string, parsed
   a second object graph, and canonicalized the parsed graph again.
3. Abrupt process death can leave the PID/UUID-stamped temporary file because
   exception cleanup cannot run after an OOM kill.
4. The 1.10 GB temporary aggregate is not a valid replacement for the 124 MB
   last-known-good checkpoint and was not used for restore.

### Strongly supported inference

The OOM occurred during the checkpoint serialization/write/read-back window.
The old algorithm could simultaneously retain the live object graph, the
complete encoded bytes, the complete read-back bytes, and a parsed read-back
graph. The unusually large temporary file and Render memory-limit restart are
consistent with this exact amplification. Precise allocation timing cannot be
proven without Render process metrics or a stack/profile captured at the kill.

### Ruled out as the primary amplifier

The persisted operations journal is bounded to 400 active entries and 40
compacted summaries. Post-recovery Remote Journal pending count fell from 48
to 24 and current lag returned within the 1,800-second SLO. It remains an
operational backlog to observe, but it does not explain a 1.10 GB checkpoint
temporary on its own.

## Minimal hotfix contract

- Canonical JSON is emitted incrementally and hashed as it is written.
- Read-back verification streams SHA-256 and checks stable file identity; it
  does not materialize or parse a second full snapshot. Because the bytes must
  equal the canonical bytes generated from a source object whose embedded
  seal was verified, equality is sufficient to prove the published JSON.
- The default maximum checkpoint is 512 MiB, configurable through
  `ARGUS_CHECKPOINT_MAX_BYTES`. Exceeding it preserves the final
  last-known-good file and removes only the current writer's temporary.
- A non-blocking OS flock on `<checkpoint>.writer.lock` enforces one writer
  across processes in addition to the existing in-process lock.
- Writer temporaries are flocked while active.
- Startup scans only the exact checkpoint PID/UUID temporary naming contract.
  It records stat metadata without loading content. Deletion requires both an
  exclusive flock and Linux `/proc/<pid>/fd` proof that the stamped writer does
  not own the same device/inode. Unknown ownership fails closed. Every actual
  cleanup is emitted as a separate structured log record.
- Final fsync, streaming read-back hash, atomic replace, directory fsync, WAL
  compaction gating, cursor and Remote Journal receipt rules are preserved.

## Rollout and rollback plan (owner approval required)

1. Merge only the reviewed v13.3.8 hotfix after all required checks pass.
2. Deploy once through the normal backend release path; do not manually tick.
3. At the new boot, capture structured abandoned-temp reconciliation evidence,
   `/healthz`, `/readyz`, exact SHA/version/boot, disk capacity and integrity.
4. Wait for the first natural EC2 systemd tick. Require HTTP 200, caught-up or
   bounded progress, verified checkpoint, WAL/receipt read-back and no restart.
5. Start a new formal Soak only from the first eligible natural tick under the
   new exact SHA. Never rewrite the interrupted v13.3.7 Soak.
6. Roll back to the last verified release if readiness fails, checkpoint size
   guard trips on normal state, integrity/read-back fails, or memory again
   approaches the Render limit. Preserve the failed build's checkpoint temp,
   WAL, receipt and logs as evidence; do not manually edit them.
