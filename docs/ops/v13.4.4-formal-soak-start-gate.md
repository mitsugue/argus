# ARGUS v13.4.4 Formal Soak start-gate safety

This is a narrow release candidate. The code, tests, and Draft PR do not
authorize a merge, deployment, restart, environment change, EC2 change, manual
workflow, mission tick, checkpoint, heartbeat, Journal flush, owner arm, or
Formal Soak start.

## Audited creation and restore paths

The only runtime creation path is
`scanner._api_argus_admin_missions_tick_impl()` calling
`scanner._activate_formal_soak()`. The latter creates the deterministic
`soakId` from the deployed build and mission-window ID. Before v13.4.4 the
expression `not _CHECKPOINT_V2_STAGE1_ENABLED` authorized this call. That
treated a disabled safety subsystem as permission and bypassed every Stage 1
resource and owner gate.

The durable owner-arm write path is
`POST /api/argus/admin/soak/arm` ->
`argus_checkpoint_v2_stage1.arm()` -> the verified legacy checkpoint plus V2
dual-write. `record_failure()` clears the arm. A successful start consumes it
with `consume_arm()` and persists the consumed-arm audit record in the same
ordinary mission checkpoint. v13.4.4 removes the competing legacy rollover
arm: Stage 1 disabled returns `stage1_not_enabled`.

Restore runs through `scanner._osint_restore_once()` and
`argus_runtime.soak_restore_decision()`. Startup/restore does not call the
activation function. A running Soak from another build, or a running Soak from
a prior boot, is copied by value to bounded history and terminalized as
`interrupted`; its ID, start time, heartbeats, and incomplete status are
preserved. No replacement is created by restore. A restored Stage 1 arm is
accepted only for an enabled Stage 1 and the exact current build; an older arm
schema lacks the v13.4.4 contract fields and therefore fails closed.

Manual and diagnostic ticks normalize to `manual`; GitHub scheduled runs
normalize to `github_schedule`. Neither satisfies the central predicate.
Duplicate mission windows are suppressed before mission execution, and the
predicate also rejects the recorded consumed window.

## Intended start contract

`formal_soak_start_eligibility()` is the single fail-closed decision. A start
requires all of the following:

- Checkpoint V2 Stage 1 is enabled.
- The live three-window resource gate passes.
- Disk acceptance, isolated restore verification, and restore-authority owner
  approval are persisted.
- `authorityPromotionBlocked` is false. V2 restore authority itself remains
  false during Stage 1; promotion is a later, separate operation.
- A durable, explicit `owner_admin` arm targets the exact 40-character build,
  the declared boot policy, and Formal Soak lifecycle version.
- No Formal Soak is active.
- The trigger is a non-manual, non-diagnostic, non-retrospective,
  non-replayed ordinary `ec2_systemd` window with its exact expected build.

Stable blockers are public-safe bounded scalars. They include
`checkpoint_v2_disabled`, `formal_soak_not_armed`,
`resource_acceptance_failed`, `authority_promotion_blocked`,
`disk_acceptance_missing`, `isolated_restore_not_verified`,
`restore_authority_approval_missing`, `validation_failure_unresolved`,
`active_soak_exists`, `trigger_not_qualified_natural`,
`mission_window_replayed`, `identity_mismatch`, and `arm_contract_invalid`.

The existing Stage 1 acceptance endpoint separately requires a current exact
Remote Journal receipt before it records acceptance. Repository evidence does
not establish a second Remote Journal read-back as part of the start-time
predicate, and this hotfix intentionally does not change Remote Journal
behavior. Whether a second start-time Journal freshness check is desired is an
owner policy question outside this PR.

## State truth

When Stage 1 is disabled, public state reports `checkpointV2.state=disabled`
and `checkpointMode=legacy_only`; it does not claim active dual writing.
`/readyz` and the public data-quality console expose the owner-arm state,
central eligibility and blockers, the active runtime Soak, and bounded
historical terminal records as separate fields. Thus a live persisted Soak
cannot be hidden behind an arm state of `not_started`.

## Current invalid Soak on a future deployment

No production state is changed by this PR. If v13.4.4 is later deployed
normally, the generic cross-build restore contract terminalizes the currently
running v13.4.3 Soak as `interrupted`, retains its ID/start/heartbeat evidence,
keeps `completed72h=false`, and creates no replacement. There is no
Soak-ID-specific code. With Stage 1 disabled and no v13.4.4 owner arm, all
subsequent natural ticks remain ineligible.

## Rollout gate

After all required checks pass, keep the PR Draft and request separate owner
approval. A later deployment must first verify the exact version/SHA/boot,
then observe the generic interruption record. Do not manually tick, arm, start,
or rewrite evidence. Any unexpected active replacement is a stop condition.
