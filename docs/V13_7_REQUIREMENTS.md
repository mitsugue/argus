## 1. 最上位原則と存在価値

ARGUSは、市場とオーナーの投資前提を継続して記憶し、現在の判断に必要な根拠を選び、LLMで統合し、その判断を結果から検証する、自分専用の投資判断の羅針盤である。

ARGUS = OSINT × Market State × Personal Context × Memory × Retrieval × Reasoning × Decision × Verification

日常の確認、解説、追加質問、通知、履歴確認はARGUS一つで完結させる。オーナーがChatGPTとARGUSを日常的に使い分けたり、毎日コピーして情報を移したりする構成にはしない。LLMは内部の推論エンジンとして利用する。

ARGUS固有の価値は、公開ニュースの量ではなく、当時の市場、利用できた情報、自分の保有前提、ARGUSの判断、その後の結果を一続きに追跡できることに置く。

蓄積量が増えるだけで予測精度が上がる、将来も絶対に代替されない、という保証はしない。判断の有用性を検証し、確認の手間と維持費に見合う働きを提供する。

最終的な売買はオーナーが判断する。13.7には自動売買、発注、証券口座操作を追加しない。独立アプリ13Mの統合も対象外とする。

## 2. 13.7の完成範囲

次を、既存の取得経路・保有監視対象・対応市場を土台に、一続きで動く状態にする。

1. OSINTと市場データを受け取り、出典と時点を保持する。
2. 重複を整理し、出来事・観測・解釈を関連づけて保存する。
3. 今回の判断に必要な現在情報、関連履歴、反証、個人情報を選ぶ。
4. 統合LLMと既存の数値エンジンから、一貫した判断・説明を作る。
5. Todayと通知で、変化、意味、見直す条件、次の確認を示す。
6. 判断・予測をその時点の根拠とともに固定し、結果を追記する。
7. 費用・鮮度・失敗・通知到達状態を記録し、無駄な処理を減らす。

着手時に、対象とする情報源、イベント種別、市場、銘柄、既存機能との対応を短く明示する。最初に代表的な一件を通し、その後、明示した対象範囲へ展開する。一件のデモ成功を全体完成とは扱わない。

専用の巨大ベクトル基盤、グラフDB、独自モデル学習、全世界ニュース対応、全過去履歴の一括移行を必須にしない。必要性が確認できた場合に小さく追加する。

## 3. 処理構成と役割

以下は論理的な役割分担であり、それぞれ別サービスとして新設する指示ではない。

| 段階 | 責務 |
| --- | --- |
| 取得 | メール、公式発表、IR、許可されたニュース、既存の市場データを取得する |
| 保存・整理 | 原典、時点、重複、訂正、対象、出来事との関係を保持する |
| 現在状態 | 市場、保有、監視、投資前提、既存サイン、重要予定の現在値を管理する |
| Retrieval | 判断目的に応じ、予算内で関連情報と反証を選ぶ |
| 統合LLM | 経緯を理解し、仮説を比較し、影響・判断案・確認事項を生成する |
| 判断の確定 | 既存の判断経路で、鮮度・欠損・リスク条件と整合させる |
| 表示・通知 | 保存済みの判断を基に、平易な説明と必要な通知を提供する |
| 検証 | 評価期限が来た予測に結果と評価を結びつける |

重要情報の取得・数値判定・簡潔な速報を、高価で長い統合LLM処理から分離する。重大な事実の通知を、全履歴の検索や長文分析の完了待ちにしない。

## 4. 記憶の論理データモデル

記事、出来事、市場観測、解釈、予測、結果を区別する。以下の概念は既存スキーマに対応づけ、不要なテーブルや台帳を重複作成しない。

| 概念 | 保存する内容 |
| --- | --- |
| Evidence | 取得した原典・本文または許可範囲の抜粋、URL・原文ID、発信元、版、取得状態、時刻 |
| Event | 個別の発表・発言・決算等の出来事、対象、分類、予定日時、状態、関連Evidence |
| Observation / Market State | 価格・金利・為替・指標・需給等の観測値、単位、対象市場、情報源、基準時刻、鮮度、改定版 |
| Interpretation / Hypothesis | 事実から導いた見方・因果仮説、支持・反対の根拠、前提、対象期間、不確実性 |
| Personal Context | 保有・監視・売却済み、確認できた数量・投資期間・保有理由・見直し条件、それぞれの更新時点 |
| Decision | 全体方針または個別銘柄への判断、時間軸、根拠、制約、次の確認、以前の判断からの変化 |
| Prediction | 判定可能な対象・期間・条件を持つ予測、作成時点の根拠、ルール・モデル等の版 |
| Outcome | 評価期限後の実際の市場・イベント結果、情報源、取得時刻、訂正履歴 |
| Evaluation | PredictionとOutcomeの照合、評価方式、成否・誤差・保留理由、評価版 |
| Run / Retrieval Record | 処理目的、基準時点、選択した情報のIDと版、選択方針、使用量、失敗・不足・省略理由 |

各記録を安定したIDで結び、訂正と更新の履歴を持たせる。金額・比率・通貨・単位、指数とETF、実測値と推計値を混同しない。原典にない値を補完しない。

ARGUSの提案、オーナーが登録した意思決定、実際に確認された売買行動は別の記録とする。未確認の売買や保有理由を推測して作らない。

保有・投資前提の更新は既存の入力・連携を活用し、必要な項目をARGUS内で確認・訂正できるようにする。未登録項目を全機能の利用条件にせず、毎日の手入力も要求しない。

## 5. OSINTの整理と信頼性

専用メールへの集約は既存の重要な取得経路として活用する。メール以外も含め、取得から記録・判断までの接続を維持する。メールが届くことだけで、重要情報を網羅できているとは扱わない。

重複処理は次の三段階に分ける。

1. 同一本文・同一配信の重複排除。
2. 同じ出来事を扱う複数Evidenceの関連付け。
3. 異なる出来事を結ぶテーマ・解釈・仮説の作成。

例えば、CPI発表とFRB関係者の発言は別Eventとして保持する。利回りの変化はObservation、利下げ期待の後退は根拠付きのInterpretation、株式への影響はHypothesisとして関連付ける。

記事を統合しても、異なる見解、数値の食い違い、訂正を消さない。統合の誤りを後から分割・訂正できるようにする。同じ通信社記事の転載を独立した裏付けとして重複加算しない。

機関投資家・金融機関等の見解は、発信者、原典、発表時点、強気・弱気・条件付き主張、対象期間を分け、関連イベントと保有銘柄に接続する。見解と実際の売買・資金フローを混同しない。

関連性は銘柄名の一致だけで判断しない。金利、為替、国、産業、需給等を通じた影響も拾う。新しい出来事は、過去の類似例がなくても重要情報として扱えること。

再受信、遅延到着、順序の逆転、再試行で、同じEvent・予測・通知が無制限に増えないようにする。継続イベントへの新事実・訂正・深刻化は差分として再評価する。

原文の取得・保存は情報源の利用条件とアクセス権限に従う。全文を保存できない場合は、許可範囲の抜粋、URL、識別情報、取得時点、制約を残す。閲覧不能な本文を推測して補わない。

メール・Web・添付内の文章は分析対象のデータであり、システムへの命令として扱わない。取得した文章から認証情報の開示、外部操作、予算・ルール変更を実行させない。保有情報、原文、認証情報を公開ログへ出さない。

## 6. 時点管理と長期保存

少なくとも以下を区別する。存在しない時刻は不明とし、取得時刻から推測して埋めない。

・出来事の発生時刻／対象期間
・情報源の公表時刻
・ARGUSの受信・取得時刻
・ARGUS内で利用可能になった時刻
・分析・判断の作成時刻
・訂正・改定の時刻と版

内部時刻は一貫して扱い、画面はJSTを基本として必要な市場の現地時刻を添える。営業日、休場、夏時間、予定変更に対応する。

実運用時の判断の再現では、その時点でARGUSが利用できた情報だけを使う。後日取得した古い記事や改定後の統計を、当時受信済みだったように扱わない。

履歴からの研究用検証は、実運用で出した予測と明確に分ける。公表時点、当時の版、使用モデルの知識による将来情報の混入など、再現の限界を記録する。過去の稼働実績を後付けで作らない。

保存は、日常的に読む現在状態・進行中イベントと、長期の原典・履歴を分ける。頻繁に使うイベント要約は更新可能とするが、原典の版や当時の判断は保持する。要約を再利用するときも根拠へ戻れること。

キャッシュや再生成可能な索引、短期の処理ログ、判断再現に必要な証跡で保持方針を分ける。古いという理由だけで判断の根拠を削除しない。保持期間と費用の関係を明示する。

既存のバックアップ・復旧機構を活かし、予測と根拠の関連が復旧後も維持されるようにする。検索索引は必要に応じて再構築できる派生物とし、唯一の記録にしない。オーナーのデータは一般的な形式で出力・移行できるようにする。

## 7. Retrieval：必要な情報を選ぶ中核機能

保存量と、一回の検索・LLMへの入力量を分離する。ただし、件数の制限だけで検索費用や品質が保証されるとは扱わない。

検索の起点は、分析対象、基準時点、時間軸、保有・監視対象、進行中の仮説、今回の変化とする。

基本手順：

1. 今回必ず考慮すべき最新の重大事実、関連する現在値、保有前提、欠損を取得する。
2. 日時、銘柄・企業、国、市場、イベント種別、関連ID等の構造化条件と索引で候補を絞る。
3. 関連イベントの経緯と、比較可能な過去の市場状態を検索する。
4. 必要に応じて全文検索・意味検索を組み合わせる。Embeddingは新規・変更分を基本にする。
5. 現在の見方に反する根拠、外れた事例、代替仮説も探す。
6. 重複、転載、ARGUS自身の過去の解釈を区別し、必要な場合だけ候補を再順位付けする。
7. 根拠付きの短い情報パッケージとして統合LLMへ渡す。

単なる言葉の類似を、市場条件の類似や因果関係の証明として扱わない。過去比較では、取得できる範囲で金利環境、景気、需給、変動性、制度・市場構造の違いを確認する。

必須の現在情報と過去の比較事例は別枠にする。最新の重大事実や反証を、類似度が低いという理由だけで落とさない。十分な比較事例がなければ、その不足を示す。

20〜50件は初期の候補目安であり、固定の正解・最低件数ではない。資料数に加え、本文の長さ、検索候補数、再順位付け数、追加検索回数、時間、費用を制限する。足りない情報が判断を変えうる場合は予算内で追加検索し、解決できなければ限定的な判断または保留とする。

各分析に、実際に選択した情報のID・版、選択理由、重要な省略・不足、検索方針の版を残す。全候補本文を毎回ログに複製しない。検索で見つからなかったことと、情報が存在しないことを区別する。

検索品質は、既知の重要情報や反証を取り出せたかで確認する。LLMの文章の自然さだけで評価しない。

## 8. 統合LLM・日本株分析エンジン等のエンジン・判断の役割

統合LLMは、単なる文章整形に限定しない。次を担う。

・ニュースと市場の時間的なつながりを理解する。
・複数の仮説、支持・反対の材料、過去との違いを比較する。
・全体市場と個別保有への影響を整理する。
・時間軸付きの判断案、反証条件、次の確認事項を作る。
・根拠不足や、結論が変わる条件を平易に説明する。

数値計算、観測値の正本、鮮度、欠損、リスク条件は既存の検証可能な処理で扱う。LLMが値を作り、古い情報を新鮮と見なし、制約を文章で解除しないようにする。

判断の最終的な製品出力は、既存のSingle Decision Authority等の一貫した経路に接続する。LLM出力から直接、別系統の売買サインを表示しない。LLMの分析案をどう採用・制限・保留したか追跡できること。

日本株分析エンジン、需給・トレンド、Seven Sign、その他の既存エンジンは役割を確認して再利用する。今回、理論を一から作り直したり、数を増やしたりしない。

日本株分析エンジンは「条件を定義し、その条件下で値動きに再現性があるかを検証する」仕組みとする。原典の主張、ARGUS独自の解釈、計算式、入力、ルール版を区別する。

エンジン間で見方が異なる場合は、対象・時間軸・根拠の違いを示す。多数決や平均だけで矛盾を隠さない。情報不足での保留と、根拠のある見送りを区別する。

モデルは、利用可能なAPIと実際の契約・料金を確認して接続する。ChatGPTの画面上のモデル名や契約を、そのままAPI利用可能性や無料利用の根拠にしない。モデル・プロンプト・検索方針の版を記録し、交換しても履歴の読み出しを維持する。

既存の対話機能を活かし、「なぜ」「前回と何が違う」「何が起きたら見直す」への追加質問をARGUS内でできるようにする。未実装なら、保存済みの判断と根拠を利用する限定的な対話から実装する。画面閲覧だけで毎回再推論しない。

## 9. Prediction Ledgerと結果検証

判断には予測を伴わないものもある。すべての解説を予測に変換せず、評価可能な主張だけをPredictionとして登録する。

予測時に、少なくとも次を固定する。

・対象市場・銘柄・指標
・作成時点、基準値、その情報源
・予測の対象、方向・範囲・条件、時間軸
・的中・不成立を判定する定義と評価期限
・反証・見直し条件
・入力Evidenceと市場状態のID・版
・根拠、不足、代替シナリオ
・使用ルール、モデル、プロンプト、検索方針の版

「3営業日後の終値が基準値を下回る」と「3営業日の途中で一定幅下落する」は別の予測とする。営業日、判定時刻、価格調整等の扱いを事前に定める。

確率は、対象事象と算出方法が明確な場合にのみ出す。LLMの自己申告の自信、根拠の充実度、過去類似例の割合を、校正された発生確率として混同しない。未校正なら表示を区別し、根拠がなければ確率を付けない。

Predictionは上書きしない。状況変化による見直しは新しい版または関連する新予測として追加し、変更理由を残す。同じ予測の更新を、独立した成功例として重複集計しない。

評価期限後に実データを取得し、OutcomeとEvaluationを追記する。未到来、データ不足、取引停止等は未評価・評価不能として残し、的中扱いしない。評価データが訂正された場合も訂正履歴を残す。

数値予測の成否は、事前の定義に従う処理で判定する。LLMは誤りの説明や仮説整理を補助できるが、自己採点だけで成功を確定しない。

評価では、対象・期間・ルール版別に標本数、誤差、誤報、観測可能な重要事象の見逃し、保留を確認する。確率がある場合は校正も確認する。予測の性質に合う単純な基準と比較する。実際の売買が確認できなければ、予測成績とオーナーの損益を混同しない。

ARGUSの過去の判断は、外部の観測事実とは別の種類として検索する。過去に同じ説明を繰り返したことを、独立した証拠の増加と扱わない。

「自分の判断の癖を学ぶ」は、まず結果から誤りの傾向を把握し、改善候補を出すこととする。13.7で自己判断による本番ルールの自動変更を追加しない。改善案は版管理し、調整に使っていない後続データで検証する。蓄積やRAGの利用と、モデル自体の学習を区別する。

## 10. Today・イベント・銘柄・通知の体験

オーナーは忙しい映像ディレクターである。最初の短い確認で、次の三つを理解できるようにする。

1. 前回の確認から、自分に関係する何が変わったか。
2. 今の見方を支える根拠は何か。どの条件で見直すか。
3. 次に、いつ、何を確認すればよいか。

Todayの基本順序は、現在の全体方針、判断に影響する重要な変化・イベント、保有・監視銘柄への影響とする。重大な新事実と重要イベントは個別銘柄一覧より先に理解できる配置にする。既存のカードや画面に統合し、重複パネルを増やさない。

最上部の説明は数文を基本とし、詳細・原典・過去比較・チャート・数式・処理状態は開いて確認できるようにする。専門用語や内部コードだけで説明を済ませない。

全体方針と個別銘柄の判断、短期と中長期を分ける。保有理由が未登録なら一般的な市場影響の説明は続け、個人の前提への判断ができない部分を示す。古い保有情報を最新と扱わない。

警戒だけでなく、既存の根拠と判断ルールに基づく保有継続、新規検討、買い増し、縮小等の条件も扱う。結論の方向を固定せず、機会とリスクの両方を説明する。

・何の発表か、日時、重要な理由、関連する市場・銘柄
・事前予想の出典と取得時点、ARGUSのシナリオ、注目する条件
・発表後の公式結果、予想との差、市場反応、見方の更新
・次の確認事項

事前予想がなければ捏造しない。結果待ち、発表延期、取得失敗、発表済み、影響継続を区別する。日付が過ぎただけで完了と扱わず、古いイベントを最重要として出し続けない。

変化のない日に新しい結論を無理に作らない。「確認した範囲で重要な変化なし」と「取得できず未確認」を区別する。出典、対象日時、判断更新時刻、重要な欠損を確認できること。

通知は、記事の新着件数ではなく、重要な事実、判断の変更、見直し条件への該当、必要な確認を中心にする。同じ出来事の反復通知を抑え、訂正・深刻化は新しい理由付きで再通知する。

検知、通知生成、送信処理、配信確認、既読は区別する。取得できない状態を推測しない。送信失敗は制限付きで再試行し、再起動しても重複や消失を抑える。

## 11. コスト設計

目的は、必要な働きを保ちながら総運用費を下げ、長期蓄積による費用増大を制御することである。保存量に比例して毎回のLLM入力を増やさない。一方で、保存・索引等も含めて永遠に定額とは約束しない。

費用を少なくとも次に分け、既存の請求・使用量記録を利用する。

・サーバー等の固定費
・市場データ、検索、ニュース等の契約・従量費
・新規取り込み、構造化、Embedding、再順位付け
・LLMの入出力、呼び出し、再試行
・原文、DB、検索索引、ログ、バックアップ、転送
・通知

請求実績、使用量からの推計、未確認を分ける。一時的な開発・移行・検証費用と、継続費用も分ける。呼び出し数が減っても固定契約料金が同じなら、使用量削減と請求額削減を区別する。

既存のSettings等で、今月の使用量・費用、推計の前提、上限、制限中の機能を簡潔に確認できるようにする。費用表示のために高価な別サービスを常設しない。

改善の優先順位：

1. 同じ取得、同じ記事、同じ分析、複数スケジューラーの重複を減らす。
2. 取得・数値判定・説明生成を分離し、変化がないときは適切に再利用する。
3. データ種別、公開頻度、市場時間、重要イベントに合わせて実行頻度を調整する。
4. 構造化・索引・Embeddingは差分更新し、モデル交換のたびの全履歴再処理を前提にしない。
5. 定型表示と決定的な処理を活かし、複雑な統合判断に必要な場合だけ高性能LLMを使う。
6. 古い原文と日常的な検索対象、短期ログと判断証跡で保存方法を分ける。
7. 依存と実際の請求を確認したうえで、不要な契約や過大なインフラを整理する。

キャッシュは、入力データの版、保有前提、ルール・モデル・検索方針の版、有効期限等の必要な条件で無効化する。訂正や判断条件の変化を無視しない。表示の日付だけ変えて再分析済みと見せない。

価格、公式統計、ニュース、深い分析を同じ頻度で処理しない。重要発表・急変時の必要な速さを維持し、市場休場だけを理由に重大な地政学ニュース監視まで止めない。

設定可能な予算として、月・日の費用、処理別の使用量、一回の入出力、検索候補・追加検索、再試行、同時実行、過去履歴取り込みを管理する。既存の上限を優先し、不明な単価や削減率を作らない。具体値は利用実績と必要な品質から設定根拠を記録する。

予算判定は実行前に行い、並行処理で上限を超えないよう既存の予約・使用量管理を活かす。高額な代替モデルや無限再試行へ自動で連鎖させない。

上限接近時は、低優先の長文解説、深掘り、過去移行から抑制する。可能な範囲で基本の取得、数値判定、重大事実の短い通知を優先する。全経路が利用不能なら監視不能を示す。古い判断を現在も有効と偽装しない。

新規の過去移行や再索引は、対象・費用・速度を制限し、中断・再開可能にする。13.7の利用開始に全履歴移行を要求しない。

## 14. 受け入れ基準

既存テストと実行記録を利用し、変更で壊れうる箇所に検証を集中する。同じ確認の反復や、高額なLLMによる全件評価を常設しない。

| ケース | 期待する動作 |
| --- | --- |
| 重要な変化がない | 取得の健全性を確認した範囲で変化なしと示し、不要な再生成を抑える |
| 重要発表の前後 | 予定・事前材料・公式結果・市場反応・見直しがつながる |
| 突発ニュース | 関連履歴がなくても重要事実を拾い、長い分析待ちで速報を止めない |
| 重複・転載・再試行 | 出来事、裏付け、予測、通知を重複加算しない |
| 原典の訂正・遅延到着 | 新しい版を保持し、現在の判断を更新しつつ当時の記録を守る |
| 反証・相反する情報 | 都合のよい材料だけで結論を作らず、相違と不足を示す |
| 過去の判断の再現 | 当時利用できた情報に限定し、後日の結果・改定を混ぜない |
| 保有前提の変更 | 新しい前提を現在の分析へ反映し、過去の前提は保持する |
| 数値エンジンとの不一致 | LLMが制約を解除せず、既存の判断経路で整合・制限・保留する |
| 予測の満期・結果不足 | 事前定義どおり評価し、不足時は未評価として残す |
| 予算上限・取得障害 | 優先処理を可能な範囲で残し、停止・古さ・制限を明示する |

| 履歴量の増大 | 全履歴の反復処理を避け、検索処理量・遅延・LLM入力・費用を観測できる |

履歴量の増大は、小さな比較試験で確認する。同じ新規流入量・分析頻度に対し、短期間分と長期間相当の履歴で処理量がどう変わるかを見る。検証用データは明示し、運用実績や予測精度の証拠と混同しない。

品質指標には、情報源の最終成功・欠損、重要情報の公表／受信から表示・通知までの遅延、既知の重要情報の検索漏れ、重複、予測評価の未処理、表示速度を含める。観測できない遅延や未知のニュース全体の網羅率を作らない。

重要情報の鮮度・通知遅延、通常表示の速度、予算等の具体的な目標値は、既存の基準と測定結果を用いて対象別に明記する。測定できない項目を合格扱いしない。費用だけを理由に既存の重要な品質基準を黙って緩めない。

費用は、同等の稼働日・対象・分析頻度など比較条件を明示して、変更前後の実績または推計を示す。実請求がまだ出ていなければ、推計削減と請求額削減の確定を分ける。

機能の完成、費用削減の観測、予測の有効性の検証は別の判定とする。短期間の試験で、長期の予測力や投資収益を証明したとは扱わない。

### 13.7.2：関連イベントの結果を当時の仮説へ接続する
